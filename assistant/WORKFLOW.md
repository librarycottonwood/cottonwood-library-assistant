# Administrator and agent workflow

## One request, one PR, one save decision

Use `librarycottonwood/cottonwood-library-assistant` and the prepared library Codex environment. Fetch current main and create a new isolated worktree and branch for each website request. Preserve other worktrees and open PRs. The separate `oobagi/cottonwood-community-library` redesign checkout is not this implementation repository.

1. Read the request, `AGENTS.md`, `assistant/CMS.md` and current setup evidence. Inspect the existing website and content before editing. Resolve routine implementation choices yourself.
2. Make the requested change on the request's branch. Current library content lives in Sanity. Use permitted Sanity tools for drafts, corrections and supported publication; do not copy content into old seed files. For a CMS-only release, add a new `content-updates/<YYYY-MM-DD>-<short-name>.json` with a one-sentence `request`, the changed `sanityDocuments` (`id`, `revision`, `fields`) and `requestedInChat`, so that the website release still has its own reviewable PR without duplicating CMS records. Each save has its own file, so open saves do not conflict. `assistant/website-update.json` is still accepted for saves opened before this change; do not use it for new ones.
3. Run `pnpm check`, `pnpm build`, relevant tests and `pnpm assistant:capture`. Open a PR. Its `pr-preview` job captures actual published Sanity content, builds the exact PR head and checks phone/desktop pages without account credentials. The ordinary `verify` job also checks fixtures; fixture pictures are not current-content previews.
4. `publish-live.yml`, running trusted main code, validates that successful PR artifact and uploads an immutable preview (`<8hex>.cottonwood-library.pages.dev`) to the library-account live project. Previews never change the live website. Read its `library-publish-live-result` artifact or workflow summary. Verify the returned URL works and inspect the affected page, navigation/forms and internal screenshots. Do not send screenshots unless asked. The same run posts the PR comment “What this save puts on the live website” (and `content-changes.json` in that artifact): every website document that differs from the live website, flagged when this PR's content-update file does not list it. Unlisted changes (often another person's unfinished save) go live with this merge; name them to the requester and ask before merging. A picture uploaded but not yet used by any document does not count as a change.
5. Give the working website preview URL in chat and ask **“Ready to save?”** Keep the PR, head commit, preview run and release digest in task context. A request merely to look at the website does not ask to save it.
6. After explicit chat approval, fetch main, preserve concurrent changes and resolve ordinary conflicts yourself. Rerun affected checks. The reviewed branch must contain the current main tree plus this request. If conflict resolution or new content materially changes the preview, show the updated URL and ask again. An unchanged checked version does not need repetitive approval.
7. Merge the PR through authenticated GitHub after its checks pass. This is the save decision; no publishing OAuth tool or external approval page is required. The successful main check triggers `publish-live.yml`, which verifies the merged tree equals the reviewed PR tree, verifies current Sanity content/revisions still match, and publishes the exact checked PR assets to the **live website**. It never rebuilds after approval. A mismatch stops the save and requires a fresh preview. Only the main check's `verify` job gates the save; failed health/record jobs do not. A stopped save posts a failed **Live website** status and a PR comment; the merge stays, the website is unchanged, and the fix is a fresh refresh PR (new branch from main, new content-update file listing the same documents, preview, approval, merge).
8. Check the merged commit, workflow result and live `/_review/status.json`. The status retains the preview's `sourceSha` and adds `mergedSourceSha`; both commits must have the same tree. Match the content/release digests and confirm the existing CMS ledger recorded the verified deployment. A source merge alone is not a completed website save.
9. After verification, remove only this task's completed worktree and branches. Archive managed worktrees using the app's archive tool; remove repository-explicit worktrees through Git. Preserve unrelated/open work, current previews and the previous verified recovery release. Declining leaves the live website unchanged.

The flow is **preview → live**. The live website is https://cottonwood-library.pages.dev/ (production deployment of the library-account Pages project `cottonwood-library`). The cottonwoodcommunitylibrary.com domain is attached to that same project at launch; see DOMAIN-LAUNCH.md. Domain launch, billing, ownership, bulk email and social publishing require their own request.

## Preview and deployment boundaries

Sanity project `2ou0xy2r`, dataset `production`, currently exposes the published content used by the website. PR builds read that public snapshot directly without CMS write/read secrets. If public reads stop working, report that exact blocker; never pass account credentials to untrusted PR code or silently use fixture content.

Only the trusted main workflow receives hosting credentials. It downloads PR artifacts into a separate temporary directory, validates source/run/content/release pins, rejects symlinks and hosting configuration/Worker files, and treats all artifact files as data. It never executes PR build scripts with deployment authority. Hosting uses only the library Cloudflare account; deploy scripts refuse any other `CLOUDFLARE_ACCOUNT_ID` or a missing library token. The live project `cottonwood-library` must have production branch `production` and no domains except its pages.dev address and the library's own cottonwoodcommunitylibrary.com names. CMS and PR promotions share one serialization lock and verified rollback. Automatic repair may not edit either path's authorization, workflows or tests.

For local preparation, use Node 24 and pnpm 11.15.1. Capture actual published content with `pnpm cms:snapshot --out output/cms/snapshot.json`; set `LIBRARY_CONTENT_SOURCE=sanity`, `SANITY_PROJECT_ID=2ou0xy2r`, `SANITY_DATASET=production`, and `SANITY_SNAPSHOT_PATH` to that file before building. `pnpm assistant:prepare` freezes the built assets; `pnpm assistant:capture -- <digest>` checks that saved release. There is no local upload path: never deploy from a laptop, the Pi or the cloud editor, never run `wrangler login`, and never use a personal Cloudflare account. Every shareable preview comes from the PR workflow above.

A PR that changes the trusted workflows is previewed by the version already on main. Its own main workflow first runs after merge; verify that first hosted save and ledger adoption before rolling out new account instructions.

## Content and recovery

The library chat handles questions, reports and content: Sanity tools edit/publish records, and its GitHub tools run the content PR, preview, approval, merge and live check (publishing skill, “Save a content change”). Codex handles website source/code/design changes. Do not recreate the site in Sites, build a new portal or assume Work can silently attach the prepared Codex environment. If a handoff is needed, preserve the request and give the actual existing editor entry point.

Publishing a Sanity record makes it publicly readable and queues the existing CMS check; it does not itself update the live website. Routine requested website saves use the PR workflow above. The existing identity-authenticated CMS review page and `cms.yml` remain recovery tools for an explicitly chosen administrator recovery, not an extra volunteer approval step. The reporting connector has no website publishing tools or scopes. Never ask volunteers to reconnect it for website editing.

Undo only the requested change: restore its source/content, prepare a new PR preview, obtain approval and verify the live website. Preserve current unrelated content. A failed upload is resolved only after the previous release is actually restored and verified; a retained pointer alone is insufficient.

## Pictures

Prepare every new photo, screenshot, poster or logo with `pnpm assistant:image -- <file> --name <short-name>`. It turns it upright, limits dimensions, removes hidden camera/location metadata and saves it in `library-files/images/`. Register it in `src/content/images.ts` and use Astro `<Image>` or `ContentImage` with real alt text and appropriate responsive sizes. Do not put photos in `public/` or bypass `scripts/images.mjs`. The build blocks unoptimized or unused pictures. Original Sanity upload privacy still needs its separate rehearsal.

## Existing coding environment

Keep the prepared `cottonwood-library-editor` and tested writable `/workspace` package/cache wrapper. Setup uses `bash scripts/cloud-setup.sh` and `assistant/START.md`. Do not replace the environment because of an old browser failure. Check dated evidence in `setup-status.json`: Safari follow-up submission failed with `DisposableStack`; environment Edit failure is separate; the actual library computer/browser is unverified. Repository edits cannot repair OpenAI's hosted client. Verify a fresh request, follow-up and hosted preview on the actual device before claiming handoff readiness.
