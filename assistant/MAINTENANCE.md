# Library maintenance

## One workflow for each job

- `check.yml`: website build, privacy/release checks, desktop/phone page checks, CMS content/migration tests, standalone Studio compilation/schema checks, and local publisher runtime tests daily at 16:37 UTC, on main saves, and on pull requests. Studio uses explicit fixture identifiers; the publisher build is a dry run. Main results are recorded in `maintenance-reports/.library-checks/<SHA>.json`. `sourceChecksResult` and `cmsLiveResult` distinguish those source checks from the live content check below. Feature pushes do not run a second copy of the pull-request check. On a pull request that only changes instructions/docs (`assistant/`, `docs/`, `plugins/`, `.claude/`, top-level `*.md`) or content-update files, `verify` runs only the install, `pnpm check`, build and unit tests (including the ones that read instructions); the fixture browser, CMS/Studio, publisher and connector checks are skipped because nothing they test changed. Instructions-only PRs also skip `pr-preview`. Main, daily and manual checks always run everything.
- `check.yml` → `cms-live`: a separate trusted-main-only read/build check, enabled only when the repository variable `LIBRARY_CONTENT_SOURCE` is `sanity`. It uses configured `SANITY_PROJECT_ID`/`SANITY_DATASET`, scopes the server-only read token to `cms:doctor` and snapshot retrieval, then builds from that frozen snapshot without passing the token to Astro. A separate status-token step calls the configured publisher’s monitor/reconciliation path: missed published revisions may prepare pending previews, never bypass approval. It never edits CMS content or deploys. Only the sanitized `library-cms-health` report is uploaded; the raw live snapshot stays out of the artifact. Before account setup this job is skipped, which is not evidence of a healthy live CMS. If Sanity is enabled but publisher configuration is missing, report the unfinished connection explicitly.
- `upkeep.yml`: one bounded Plus Codex repair attempt when the exact current-main website check fails. It also maintains the stored managed sign-in weekly. It does not use OpenAI API credits. The trusted worker validates an allowlisted patch, preserves concurrent saves, verifies the committed source through the complete current check, and prepares a fresh CMS preview through reconciliation. Website publication still needs a current PR preview and explicit chat approval before merge. A failed CMS check is evidence for investigation, not authority to rewrite the library’s content or weaken its validation. Credential/permission failures require guided recovery rather than a code repair.
- `publish-live.yml`: a lock-free `route` job first decides what the finished check asks for; scheduled checks, superseded PR heads and direct pushes stop there. After a PR check whose `verify` and `pr-preview` jobs passed, a per-PR `preview` job validates and hosts its exact current-content artifact as a preview and comments the list of content differences from the live website (flagging documents the PR's content-update file does not list). After the approved PR merge and a passing main `verify` job, the `publish` job (the only part holding the shared live lock) requires identical source trees and unchanged website content (unused uploads ignored), then publishes those assets to the live website (production deployment of the library-account `cottonwood-library` Pages project) with verified rollback. Every failure posts an explicit **Website preview** or **Live website** failure status. An instructions-only PR (classified again by trusted main code from GitHub's file list) gets a successful **Website preview** and, after merge, **Live website** status saying "No website change"; nothing is previewed or published and the live website stays as it was. PR builds never receive hosting/CMS-write credentials. A source callback records the verified release in the existing CMS ledger. Read both the workflow and hosted status before reporting success.
- `stale-saves.yml`: daily, closes content-save PRs (every changed file is a content-update file) with no activity for 14 days, comments that nothing went live and that Sanity changes are not undone, deletes their branches and prunes their previews. Code PRs are never touched. Manual runs default to a dry run.
- `cms.yml`: existing signed-webhook previews and administrator recovery publishing. The identity-authenticated review page remains an explicitly chosen recovery tool, not an extra approval step for normal PR saves. Both publishing workflows share the same live publishing lock.
- `live-hosting-setup.yml`: one-time, manual creation/confirmation of the live Pages project on the library Cloudflare account. It never deploys. Every deploy script refuses unless `CLOUDFLARE_ACCOUNT_ID` is the library account and a library API token is supplied; no personal account or `wrangler login` is ever used.
- `sanity-backup.yml`: weekly CMS backup, Sundays at 10:13 UTC, and on demand. Read-only. See "CMS backups" below.
- `analytics.yml`: read-only hosted Analytics connection check daily at 16:47 UTC. Record safe status/next human step in `.library-analytics-checks/`, and maintain one open issue for unresolved access. It stores no visitor counts or secrets. This check does not itself spawn a repair agent for a remote connection failure. Source/protocol failures are detected by `check.yml`; connector changes require reviewed technical work.
- `analytics-deploy.yml`: publish checked connector code only when its current live reader is usable. Missing Google approval records account_setup_pending and leaves the existing deployment alone. After publishing, wait for bounded exact-source propagation, verify a real report, and roll back a failed update. Outcomes are in `.library-analytics-deployments/`. It deploys only when `connector/` changed since the source the hosted connector reports; otherwise it stops after one quick lookup and keeps the last record.
- `cms-publisher-deploy.yml`: deploy the current checked main source to the existing CMS publisher Worker using a token restricted to that Worker. Preserve secret bindings, verify hosted source/configuration, and restore the previous Worker version if verification fails. This updates the publishing service; it cannot approve a website update. Missing deployment access skips setup explicitly.
- ChatGPT: **one weekly cloud review**, scheduled for Monday afternoon around 14:00 Pacific. The existing task was resumed October 20 and its enabled state read back. Two runs through **Run now** posted checked results; the second completed without permission questions. Its chat is unarchived in Maintenance. Confirm its current state before promising a future run. `assistant/tasks/weekly-maintenance.md` is its canonical instructions; the task's ChatGPT prompt is the short pointer in `assistant/tasks/weekly-maintenance-pointer.md`, which reads that file from main on every run. It reports the active fundraiser's Givebutter total but never edits the site (the site shows Givebutter's live donation form and goal bar). The other scheduled task prompts live beside it (see `assistant/tasks/README.md`). Its runs post into the ChatGPT **Maintenance** project, whose instructions are kept in `assistant/projects/maintenance.md`. It reviews actual repairs, current checks and account steps, then gives a friendly short summary. A healthy weekly message is welcome. Immediate repair-event notifications are not part of the required workflow.

## Repair and credential boundaries

The repair container receives website/connector source and Plus authentication, never GitHub write authority, Cloudflare publishing tokens or the credential-encryption key. Trusted host helpers reject workflow/test/security changes, public content changes, deletions, broad patches and symlinks. One bounded attempt per source avoids loops. Unresolved failures create library-assigned issues. Account access/recovery remains with the library.

The combined website/report connector is entirely outside automatic repair scope, including its formatter, MCP handler and dependency files. The retired publishing binding demonstrated that Worker modules share runtime authority; limiting function arguments was not isolation. Removing that binding does not reopen automatic edits to reporting authentication or deployment code. Protocol or presentation fixes therefore require reviewed changes. Website component/layout/style and CMS adapter repairs remain bounded as before.

The CMS extension permits only technical adapter/repository repairs in the exact allowlisted files `src/content/sanity.mjs` and `src/content/repository.ts`, alongside the existing component/layout/style repair scope. Studio dependency upkeep may update existing exact dependency versions in `studio/package.json` and its lockfile; it may not change scripts, package metadata, or add dependencies. The complete CMS, Studio, and publisher checks must pass before a repair is saved. None of this authorizes automatic changes to Sanity records, schemas, migration sources, editorial facts, workflows, tests, publisher authorization, secrets, Google access, or billing. A necessary fix outside that boundary is reported for reviewed technical work rather than forced through the repair worker.

Secrets live in GitHub/Cloudflare settings. Encrypted refreshed Plus state is stored in private artifacts; plaintext keys and logins never belong in source or artifact reports. Google short-lived access renews from an encrypted browser grant. Restored access requires a successful read-only report; signing in alone is not proof.

Healthy website checks consume GitHub allowance, while repairs and the weekly review consume shared Plus allowance. GitHub allowance is finite: the configured $0 overage stop and artifact-retention caps remain necessary. Keep at most three archives per named source/CMS/result category, with a combined 450 MiB cap (the newest four CMS backups count first); retain small health reports briefly. PR previews that can still go live (open PR heads and PRs merged in the last two days) are never pruned; previews of closed PRs and superseded heads are deleted first. An older approval whose checked artifact expired (7 days) requires a fresh preview and fresh approval. A hosted preview URL does not replace the immutable artifact required for publication. Avoid duplicate check runs and unneeded agent retries. No paid API, cloud billing or email/social sending is enabled. Sanity’s nonprofit application was submitted October 20; its decision is pending. Do not add a card, enable AI-credit features, buy a plugin, or assume unlimited free usage. CMS hosting/storage, exports, retained releases, and checks must fit existing free allowances; reaching a limit pauses the affected work and gets a plain explanation, not an unapproved upgrade.

## CMS backups

Every Sunday, `sanity-backup.yml` saves a copy of everything in Sanity (events, news, notices, newsletters, settings) together with its pictures and PDFs. It only reads; it never changes Sanity or the website.

- **Where:** GitHub → Actions → **Weekly CMS backup** → newest green run → **Artifacts** → `library-cms-backup`. Only people with access to the repository can download it. The newest four backups (about a month) are kept; older ones are deleted to stay inside the free GitHub storage (each is about 18 MB). Artifacts also expire after 90 days.
- **Download:** click `library-cms-backup` on that run (you get a zip holding `sanity-backup-<date>.tar.gz`), or run `gh run download <run id> -R librarycottonwood/cottonwood-library-assistant -n library-cms-backup`. Take a fresh copy by hand any time: Actions → **Weekly CMS backup** → **Run workflow**.
- **What is in it:** the same `.tar.gz` layout `sanity dataset export` makes (`data.ndjson`, `assets.json`, `images/`, `files/`). Without the optional `SANITY_READ_TOKEN` secret (a Sanity **Viewer** token) it holds the published records only, and pictures are the full-size copies Sanity's public image server hands out (same size and look; not always the identical file). With that secret set, unsaved drafts and the original picture files are included too. The run's summary shows the counts.
- **Restore** (a person signed in to the library's Sanity account with permission to edit; never by automatic repair). From `studio/` after `pnpm install --frozen-lockfile`, sign in with `SANITY_STUDIO_PROJECT_ID=2ou0xy2r SANITY_STUDIO_DATASET=production node scripts/run.mjs login`, then:
  1. Practise first into a spare dataset: `SANITY_STUDIO_PROJECT_ID=2ou0xy2r SANITY_STUDIO_DATASET=production node scripts/run.mjs dataset import sanity-backup-<date>.tar.gz restore-test` (needs room for a second dataset on the plan). Check it, then delete it.
  2. To put back deleted records only: the same command with `production --missing`. To also turn changed records back to the backup's version: `production --replace` (records added after the backup stay). Do this only with the board's approval, then save a website change so the live website is rebuilt from the restored content.
- **If it fails:** the weekly review reports a missing backup. The earlier copies are still there. Usual causes are Sanity being unreachable or a picture that will not download; run it again by hand, and if it keeps failing, treat it as reviewed technical work.

## Renew the repair sign-in

The repair worker uses the library ChatGPT account (librarycottonwood@gmail.com). Its weekly run keeps that sign-in fresh. If a run fails because the sign-in was rejected or revoked, guide Todd through these steps on a computer with Node and the GitHub CLI signed in to the library account:

1. `npm install --global @openai/codex`
2. `mkdir -p ~/.library-codex-login && CODEX_HOME=~/.library-codex-login codex login`. In the browser, sign in with the library email and password, not "Continue with Google" (that asks for a phone code).
3. `gh secret set LIBRARY_CODEX_AUTH_SEED -R librarycottonwood/cottonwood-library-assistant < ~/.library-codex-login/auth.json`
4. Remove the stored rejected sign-ins, which the worker would otherwise prefer: `gh api 'repos/librarycottonwood/cottonwood-library-assistant/actions/artifacts?name=library-codex-auth' --paginate --jq '.artifacts[].id' | xargs -I{} gh api -X DELETE repos/librarycottonwood/cottonwood-library-assistant/actions/artifacts/{}`
5. `gh workflow run upkeep.yml -R librarycottonwood/cottonwood-library-assistant`, then confirm that run succeeds.
6. `rm -rf ~/.library-codex-login`. Using that copy anywhere else would sign the worker out again.

## CMS status and evidence

The native Studio and website publishing path are connected and verified. `LIBRARY_CONTENT_SOURCE=sanity` is enabled. The official Sanity plugin was connected October 20; actual read, private event drafting, correction and discard succeeded in normal Safari chat. Full ChatGPT-to-website publication, nonprofit approval and recovery remain separate acceptance checks. A failed or expired ChatGPT content connection is distinct from a broken website/publisher: use the actual reconnect screen, then retry the original operation. Do not reinstall an existing plugin or infer permanent authorization from an earlier success. In Sanity mode, unavailable or malformed CMS content fails the build; it must never silently mix in local sample content.

Treat these as separate facts:

| Evidence | What it establishes |
| --- | --- |
| Exact-source `check.yml` success | Source and local runtime checks passed for that commit. Fixture identifiers are not library account access. |
| `cmsLiveResult: success` plus `library-cms-health` | Actual published records were read and rendered from one validated snapshot, and the publisher status/reconciliation check completed. No new approval or deployment was performed; any hosted verification is identified separately per operation. |
| Sanity draft saved/imported | Work is saved as a draft. Nothing was published to Sanity or the website. |
| Sanity published record | The CMS record is available to the publishing path. The website may still show the previous version. |
| Publisher `review_required` | A checked immutable website preview is ready for a person’s approval. |
| Publisher `publish_queued` | Approval was recorded and publication requested. The deployed result is not yet verified. |
| Publisher `deployed_verified` | The controlled publisher independently verified the approved operation/source/content/release against the live website's hosted status. |
| Publisher `setup_pending`, failed, uncertain, or superseded state | Explain the actual next step. Do not translate it into success or retry blindly. |

The publication gate binds document revision, source commit, content snapshot digest, immutable release digest, and checked workflow run. A content or code change invalidates the old approval. Duplicate or ambiguous deliveries are tracked in the operation ledger to avoid duplicate publishing. The service’s configuration health response alone is not proof of live publishing.

Inspect the exact `cms.yml` run, its operation/publish reports, the authenticated publisher operation status, and the hosted status before calling a CMS update verified. Reconciliation may recover a missed delivery by preparing a fresh preview, but it may not invent approval or silently publish different content. Build failures retain the current website. A deployment-verification failure remains unresolved until restoration or a new exact update is itself verified; do not promise rollback merely because a rollback path exists in source.

## Explaining incidents to the library

Use the existing weekly Maintenance review as the required delivery path. A ledger entry or a GitHub issue is not proof that an immediate ChatGPT notification was delivered. Report the request’s result, whether the current website is available, and the one next action that matters. Do not include private records, tokens, donor details, raw provider errors, or speculative causes.

- Content saved, build failed: “Your update is saved, but its website check did not finish. Your current website is still available.”
- Verified repair: “A display problem was fixed and checked. Your approved update is now visible on the live website.” Only say this after inspecting actual save, checks, and hosted verification.
- Reconnection needed: “Your update is saved. The website connection needs approval before it can continue.” Give only the verified recovery link, then check real access after the person finishes.
- Still awaiting setup: “The new editing system is waiting for the library’s account setup.” This is unfinished setup, not a new outage.
